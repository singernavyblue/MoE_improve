# 产品设计文档：多模型推理诊断与可信融合系统

## 1. 产品定位

这是一个面向复杂问答与选择题场景的多模型协作系统。它不把“模型答案不同”简单视为投票问题，也不强制把所有推理过程塞入统一模板；系统要回答的是：

> 多个模型为什么得出不同结论？哪些推理或证据可靠？在证据足够时，如何安全地融合为更可信的最终答案？

产品的核心能力是把多模型推理从“答案聚合”升级为“问题分类、差异诊断、证据验证和安全决策”。

## 2. 目标与非目标

### 2.1 产品目标

- 对答案不一致的问题，定位差异的可能来源，而非只寻找字面矛盾；
- 按题型和错误机制选择合适的分析流程；
- 将关键证据组织成可回溯、可复查、可逐步积累的主张体系；
- 只有直接证据充分时才改变原始聚合答案，避免“改错正确答案”；
- 为研究者提供可解释的实验记录，支持技术路线比较与论文论证。

### 2.2 非目标

- 不承诺自动覆盖所有推理链中的全部主张；
- 不用模型数量或答案多数代替证据；
- 不追求对每道题强行干预；
- 不试图用一种固定的推理槽位覆盖数学、理化、知识问答和开放问题。

## 3. 目标用户

| 用户 | 核心诉求 |
|---|---|
| 多模型研究者 | 了解答案差异来源，验证新方法是否真实改善而非偶然涨分 |
| 算法工程师 | 获得可恢复、可审计的流水线与明确的失败原因 |
| 项目导师/评审者 | 快速判断技术路线解决的科学问题、适用范围和实验证据 |

## 4. 核心产品流程

~~~mermaid
flowchart LR
  A[输入：题目与多模型推理链] --> B[问题类型识别]
  B --> C[答案差异与错误成因诊断]
  C --> D[按类型抽取或新增关键主张]
  D --> E[检索相关证据并独立验证]
  E --> F{证据能否直接影响答案?}
  F -- 是 --> G[受证据约束的答案融合]
  F -- 否 --> H[保留原始聚合结果]
  G --> I[可解释报告与主张库更新]
  H --> I
~~~

系统先判断“应如何分析这道题”，再判断“是否值得干预最终答案”。

## 5. 主要功能

### 5.1 问题分类器

识别题目的推理形态和适用流程，例如：

- 数值计算、公式推导；
- 因果/机制解释；
- 条件判断与逻辑约束；
- 事实知识与实体关系；
- 开放性或发散性问题。

分类结果不是最终答案，而是后续主张粒度、验证方法和融合策略的路由依据。

### 5.2 答案差异诊断器

当模型答案不一致时，分析差异可能来自：

- 事实或概念错误；
- 条件遗漏、范围不一致；
- 公式、代入或计算错误；
- 实体混淆；
- 证据不足或推理链表达不完整；
- 模型答案虽不同、但关键推理并无可验证冲突。

输出应包含“差异类型、涉及片段、置信度、是否值得进入验证”的诊断卡片。

### 5.3 动态主张管理器

对可验证的关键步骤建立结构化主张，而不是预设一套静态槽位。

每条主张至少包含：

- 实体、属性、条件、方向或取值；
- 原始推理链中的精确证据片段；
- 所属问题类型和主张类别；
- 与其他主张的支持、冲突或包含关系。

当新问题不适合现有类别时，系统允许标记为“新增主张类型”；后续通过人工或模型辅助合并同类项，逐步形成可演化的主张分类树。

### 5.4 证据验证器

对已定位的关键主张或冲突，生成不含选项和原始答案的独立验证问题，并让多个验证模型分别回答。

验证器输出三层状态：

- 强证据：至少两路独立、具体且一致的答案；
- 冲突证据：验证模型本身给出不兼容结果；
- 未知：信息不足、格式无效或无法可靠解析。

### 5.5 安全融合器

融合器不以“谁投票多”作为唯一规则，而遵循：

1. 证据必须可追溯到原始推理或独立验证；
2. 证据必须直接影响待决问题，而不只是相关；
3. 若证据只排除部分选项，应作为局部约束使用；
4. 若没有直接、充分的证据，保留原始 A-pool。

这使系统可以“少改但不乱改”。

### 5.6 实验与审计面板

面向研究和汇报，提供：

- 各题的模型答案、诊断结论、证据链和最终决策；
- 不同题型上的准确率、修正数、破坏数和净收益；
- 主张保留率、冲突定位率、验证成功率、直接证据授权率；
- 失败样本聚类，例如解析失败、题型误分、证据间接、无法映射到选项。

## 6. 关键产品原则

| 原则 | 产品含义 |
|---|---|
| 先分类，后处理 | 不同题型采用不同的主张与验证策略 |
| 先归因，后干预 | 先解释答案为何不同，再决定是否修改答案 |
| 原文优先 | 每个有效主张必须能回链至原始推理片段 |
| 动态演化 | 新问题可新增主张类别，历史主张可逐步合并 |
| 保守决策 | 无直接证据时不替换原始答案 |
| 评估防虚高 | 同时报修正数、破坏数和净收益，而非只报最终正确率 |

## 7. MVP 范围

第一阶段建议只覆盖“存在明确答案分歧、且可验证”的封闭题，优先支持数理计算、事实知识和条件判断三类。

MVP 包含：

1. 基础题型分类；
2. 推理片段检索与差异诊断；
3. 动态主张记录；
4. 多模型盲验证；
5. 直接性审查和安全回退；
6. 单题审计报告与批量实验汇总。

开放性写作、价值判断、创意生成等发散问题先只做“差异描述”，不进入自动答案融合。

## 8. 成功指标

产品成功不应只看准确率。建议分三层评估：

| 层级 | 指标 |
|---|---|
| 诊断质量 | 题型分类准确率、错误成因标注一致性、关键片段召回率 |
| 证据质量 | 主张来源可追溯率、盲验证一致率、直接证据授权率 |
| 决策质量 | 修正数、破坏数、净收益、相对 A-pool 的配对显著性 |

底线指标是：任何最终答案变化都必须能关联到获授权的直接证据。

## 9. 迭代方向

### 阶段一：建立可靠闭环

完成题型分类、关键片段定位、盲验证、直接性审查和安全回退，并沉淀失败样本。

### 阶段二：形成动态主张库

从高频问题与错误机制中归纳初始类别；允许新类型进入待归并队列，逐步形成跨题型可复用的主张图谱。

### 阶段三：做路线级比较

比较“全量 Claim 抽取”“span-first 冲突定位”“题型专用诊断”等路线在不同问题类型上的收益和代价，明确每条路线的适用边界，为论文选题提供证据。

## 10. 当前原型的对应关系

当前 span-first 混合模块可作为 MVP 的“关键片段定位 + 独立验证 + 安全回退”能力底座。后续最重要的产品化补齐是：

- 在入口增加问题分类和错误成因诊断；
- 将静态 Claim schema 改为动态、带版本的主张类型；
- 将验证事实到选项的关系从“唯一映射”扩展为“局部约束”；
- 建立面向失败样本的分析面板与主张库运营机制。
