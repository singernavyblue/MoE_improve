# 多模型推理诊断方法：实验技术方案

## 1. 目的与范围

本方案服务于方法验证阶段，而非产品开发阶段。

研究目标是验证“问题分类 + 差异归因 + 动态主张 + 独立证据验证 + 安全融合”是否能相对 A-pool 和现有 Claim 路线带来可靠净收益。系统必须支持快速修改技术路线、固定条件下重复运行、逐题审计和严格消融。

本阶段不建设 Web 产品、用户系统、微服务、在线数据库或知识图谱平台。

## 2. 设计原则

1. **可复现优先。** 每次实验必须绑定数据版本、模型快照、提示词、配置、代码版本、随机种子和完整产物。
2. **逐题可审计。** 任何答案变化都能回溯至原始推理片段、验证问题、模型回答和门控决策。
3. **配置驱动。** 技术路线和门控只通过配置切换，不通过手工改代码制造对照组。
4. **安全回退。** 证据不充分时保留 A-pool；报告修正数与破坏数，而非只报告准确率。
5. **先轻后重。** 先使用文件型实验资产与离线分析，只有在实验需求明确时才引入服务化组件。

## 3. 推荐技术栈

| 领域 | 技术选择 | 本阶段用途 |
|---|---|---|
| 主语言 | Python 3.11+ | 推理流水线、规则、评估和数据处理 |
| 依赖管理 | pyproject.toml + uv 或现有 Conda 环境 | 固定 Python 包与可复现实验环境 |
| 实验配置 | Hydra + YAML | 管理数据切分、模型组合、提示词版本、门控与消融 |
| CLI | Typer 或 argparse | 启动单阶段、全流程、评估和导出任务 |
| 模型推理 | vLLM + OpenAI 兼容接口 | 单 GPU 顺序加载本地模型 |
| 模型适配 | 自研 ModelAdapter | 统一模型名、请求格式、重试、结构化解析和原始日志 |
| 结构化约束 | Pydantic + JSON Schema | 校验分类、主张、证据、决策；格式失败显式降级 |
| 原始产物 | JSONL | 保存冻结题目、推理链、模型响应和逐题审计记录 |
| 派生分析表 | Parquet | 保存 span、Claim、证据、指标和错误标签 |
| 离线分析 | DuckDB + Jupyter Notebook | 对多轮实验和 Parquet 结果进行查询、统计和 case study |
| 实验追踪 | MLflow | 记录参数、指标、标签、图表和 artifact 路径 |
| 测试 | pytest | 覆盖确定性规则、结构验证和回归样本 |
| 图表 | Plotly / Seaborn | 生成论文和汇报所需的对比图、错误分布图 |

## 4. 总体结构

~~~text
configs/            实验与消融配置
prompts/            版本化提示词
src/
  adapters/          模型服务适配层
  schemas/           Pydantic 数据结构
  pipelines/         分类、诊断、主张、验证、融合阶段
  rules/             确定性门控与符号规则
  metrics/           指标计算、配对比较、错误归因
  io/                JSONL/Parquet/MLflow 读写
scripts/             CLI 和批量运行入口
data/
  raw/               冻结输入，不在运行时覆盖
  splits/             固定样本切分与人工标注
artifacts/
  runs/<run_id>/      单次实验的完整输出
notebooks/            分析和可视化
tests/                单测与固定回归集
docs/                 技术方案、实验协议和结果说明
~~~

现有 span-first 模块可先放入 pipelines，保持其独立可运行；后续新增的题型分类和错误归因应作为上游阶段，而不是直接塞入 pooler。

## 5. 实验运行模型

一次实验由一个不可变的 Run Manifest 描述：

~~~yaml
run_id: generated-id
dataset_id: gpqa-v1
split_id: disagreement-198-v1
code_revision: git-sha
seed: 42
models:
  - qwen
  - mathstral
  - biomistral
pipeline:
  route: span_first_hybrid
  classifier: enabled
  diagnosis: enabled
  directness_guard: enabled
  hbr_dedup: enabled
prompts:
  classifier: prompts/classifier/v1.yaml
  localizer: prompts/localizer/v3.yaml
~~~

每次运行必须落盘：

- manifest；
- 原始输入快照及其哈希；
- 每个阶段的逐题 JSONL；
- 解析失败、重试和跳过原因；
- 逐题最终答案与 A-pool 对比；
- 汇总指标、图表和人工审计样本。

不允许以同一输出文件覆盖不同配置的结果。

## 6. 关键数据对象

实验阶段不需要数据库，但需要稳定 schema。

| 对象 | 关键字段 |
|---|---|
| Record | 题目、选项、gold、A-pool、冻结推理链、初始答案 |
| ProblemType | 题型、置信度、所选分析路线、理由 |
| Diagnosis | 差异类型、相关 span、是否可验证、失败原因 |
| Span | 原始 offset、模型、文本、符号/词项特征 |
| Claim | 实体、属性、条件、方向、来源 span、类别版本 |
| Evidence | 验证问题、各模型独立回答、归一化结论、证据等级 |
| Decision | 证据直接性、可排除选项、最终答案、回退原因 |

其中 Record、Span、Claim、Evidence、Decision 应通过 ID 关联，而不是将所有信息拼成一段提示词。

## 7. 核心实验路线

### 7.1 对照路线

至少保留：

1. 原始 A-pool；
2. 旧版全量 Claim 抽取；
3. 当前 span-first 冲突定位；
4. 加入题型分类与差异诊断后的新路线。

不同路线必须使用相同的冻结模型回答、相同数据切分和相同最终评估脚本。

### 7.2 消融顺序

建议按最小增量开展：

1. 仅题型分类是否提升诊断质量；
2. 分类后使用题型专用主张模板；
3. 加入差异归因；
4. 加入动态“新增主张类型”；
5. 加入独立验证和直接性审查；
6. 比较不同融合策略。

每一步同时报告候选规模、定位调用数、有效证据数、修正数和破坏数。

## 8. 指标体系

### 8.1 决策指标

- A-pool accuracy；
- final accuracy；
- fixed：原先错误、最终正确；
- broken：原先正确、最终错误；
- net gain = fixed - broken；
- 配对显著性检验。

### 8.2 过程指标

- 题型分类准确率；
- 错误归因一致性；
- 关键 span 召回率；
- 主张来源可追溯率；
- 冲突或差异诊断的精确率；
- 验证答案格式成功率；
- STRONG 证据比例；
- 获 DIRECT 授权的证据比例；
- 每题模型调用次数与耗时。

任何 final answer 的变更都应能检查到对应的 DIRECT 证据 ID；否则计为实验错误。

## 9. 测试与质量门

### 9.1 单元测试

优先覆盖确定性部分：

- span offset 无损与全文覆盖；
- 直接答案片段不进入候选；
- 跨模型 pair 限制；
- 公式、希腊符号、HBr 别名的字段匹配；
- 同向表述不得被判为冲突；
- 条件不对齐不得进入验证；
- 无直接证据时不得改变 A-pool。

### 9.2 回归集

建立 20 至 50 道人工审计题，覆盖：

- 真正事实冲突；
- 同义改写；
- 同向假冲突；
- 条件错配；
- 实体错配；
- 数学计算；
- 理化机制；
- 文科或发散问题。

任何提示词、规则或模型适配改动都应先跑回归集，再进入 198 题或全量评估。

## 10. 阶段性交付

### 第一阶段：实验可复现

- 统一配置、Run Manifest、JSONL/Parquet 输出；
- 固定评估脚本；
- MLflow 记录实验参数和指标；
- 建立基础回归集。

### 第二阶段：验证科学假设

- 完成题型分类和差异归因的标注小集；
- 比较 span-first、全量 Claim、题型专用路线；
- 输出逐题失败归因和路线适用边界。

### 第三阶段：沉淀论文证据

- 固定最终协议和样本切分；
- 执行完整消融；
- 导出可复现结果表、案例和错误分析；
- 形成“方法在哪类问题有效、为何有效、在哪类问题无效”的结论。

## 11. 暂不引入的组件

下列组件当前会增加维护成本，但不直接验证研究假设：

- 微服务、Kubernetes、消息队列；
- PostgreSQL、Redis、线上账户系统；
- Next.js 产品前端；
- Neo4j 图数据库；
- 独立向量数据库；
- 通用 Agent 编排框架。

当出现多人并发、跨实验大规模主张复用、在线交互或 GPU 集群调度需求时，再逐项评估引入。
